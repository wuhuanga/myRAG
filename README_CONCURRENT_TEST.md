### 关键指标说明

#### 1. 时间戳格式

```
[12:34:56.123]  ← 精确到毫秒
[Upload-0]      ← 线程标识
[INFO]          ← 日志级别
```

通过时间戳可以：
- 观察任务是否真正并发启动
- 分析任务完成的时序
- 发现潜在的阻塞问题

#### 2. 并发效率

**计算公式**：
```
并发效率 = (所有任务总耗时) / (实际总耗时)
```

**示例**：
```
任务1耗时: 14.33s
任务2耗时: 13.66s
总耗时: 27.98s

并发效率 = (14.33 + 13.66) / 27.98 = 1.00x
```

**解读**：
- `1.0x` - 串行执行，无并发加速（有锁）
- `2.0x` - 完美并行，2个任务同时执行
- `0.5x` - 性能退化，可能存在问题

#### 3. 预期值对比

| 测试场景 | 预期并发效率 | 原因 |
|---------|------------|------|
| 同一实例并发上传 | ≈ 1.0x | 锁机制保护，串行处理 |
| 不同实例并发上传 | ≈ 任务数 | 完全隔离，真正并行 |
| 同一实例并发查询 | > 1.0x | 读操作通常可并发 |
| 不同实例并发查询 | ≈ 任务数 | 无锁竞争，完全并行 |

- 线程创建开销过大
- 网络延迟不稳定
- 服务器资源不足

**解决方法**：
```bash
# 减少并发数
# 编辑 test_concurrent_api.py，修改 max_workers
```

### 问题2：同一实例上传并发效率 >> 1.0x

**可能原因**：
- 锁机制未生效
- 存在数据竞争风险

**验证方法**：
```bash
# 检查文档状态是否一致
curl http://localhost:8000/api/documents/status/satellite_project

# 查看后端日志是否有并发错误
```

### 问题3：部分任务失败

**可能原因**：
- 超时设置过短
- 服务器负载过高
- 文件路径错误

**解决方法**：
```python
# 增加超时时间
timeout=300  # 改为 600

# 检查文件是否存在
ls -lh /root/workplace/lightrag/LightRAG1/docx/
```

### 问题4：不同实例并发效率 ≈ 1.0x

**可能原因**：
- 实例间意外共享了锁
- 资源竞争（CPU/内存）
- 配置错误

**排查步骤**：
1. 检查实例是否使用不同的 workspace
2. 查看系统资源使用情况
3. 检查后端日志

## 🎓 理解并发测试

### 为什么同一实例要用锁？

```python
# 场景：两个线程同时上传文档
Thread-1: 读取 index → 写入文档A → 更新 index
Thread-2: 读取 index → 写入文档B → 更新 index

# 不加锁的问题
Thread-1: 读取 index (文档数=0)
Thread-2: 读取 index (文档数=0)  ← 都读到0
Thread-1: 写入文档A, 更新 index=1
Thread-2: 写入文档B, 更新 index=1  ← 覆盖了Thread-1的更新！

# 结果：丢失了Thread-1的文档A
```

**加锁后**：
```python
Thread-1: 获取锁 → 读取 → 写入 → 更新 → 释放锁
Thread-2: 等待锁 → 获取锁 → 读取 → 写入 → 更新 → 释放锁
```

### 为什么不同实例可以并行？

```python
# 每个实例有独立的：
satellite_project/
├── workspace/          ← 独立的工作目录
├── lock               ← 独立的锁
└── index              ← 独立的索引

tender_docs/
├── workspace/          ← 独立的工作目录
├── lock               ← 独立的锁
└── index              ← 独立的索引

# 完全隔离，互不干扰
Thread-1 操作 satellite_project  ┐
Thread-2 操作 tender_docs         ┘ 可以同时进行
```
